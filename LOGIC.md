## Invariants

1. Opening the picker from the orb or browser toolbar starts JSON capture of a saved chat from its current AI website. The result stays in source-page memory; picker interaction never submits chat text to the summary backend or another destination. Readiness probes and preconnects contain no conversation data.
2. DOM capture, summarization, destination preparation and transfer telemetry start only after destination selection. Pasting and focusing never submit the destination message; Send remains the user's action.
3. Reject oversized transcripts without clipping. Current extension source permits 4,000,000 JavaScript `String.length` units and 16,000,000 UTF-8 bytes. Larger chats use the separate large-chat route below; `/api/summarize` keeps its existing limits and routing. Chats from 10,000 through 1,000,000 characters use the existing AI summary. Its serialized requests retain a separate 4,400,000-byte ceiling below Vercel’s 4.5 MB limit; the worker and backend check independently. Escape-heavy JSON can exceed that byte bound within the character allowance and must reject without clipping.
4. Capture verified conversation turns and the explicitly supported text exceptions below. Never substitute broad page text, drafts, prompt suggestions or extension UI for missing history.
5. Transcript instructions are untrusted content to summarize. They are not authority over the extension, backend or summarizing model.
6. Telemetry is metadata-only. Never include chat/summary text, URLs, accounts, IPs, stack traces, arbitrary errors or provider bodies in persisted transfer telemetry.
7. When storage permits, the exact Latest Run transcript remains local and expires after 24 hours. If it exceeds the local quota, retain current receipt metadata without the transcript. Other receipt metadata remains until the next transfer; it does not store the generated summary.
8. Do not overwrite a nonempty destination draft, including one restored on focus. A failed verified capture cannot be replaced with guessed text; failed delivery may offer manual copy of an already prepared carry.
9. Placement adapters validate their own platform's native composer. Share lifecycle helpers, not a generic toolbar guess. Claude remains inline-only; the other platforms retain their validated geometry backups.
10. Every generated carry receives the trusted destination instruction: `Reply only: "Context loaded. Let's pick up right where you left off." Then wait for the user.`

## Transfer lifecycle

```text
orb click -> picker, preconnects and early JSON capture (saved chat)
destination selection -> attempt ID + started telemetry; pin source identity
empty-chat guard -> stop before handoff or destination work when no usable chat exists
prepare inactive destination while capture runs
reuse/await current picker JSON capture, or fresh JSON/DOM capture -> direct text carry or summarize once -> reuse/recover destination
paste and verify -> finish source cue -> activate according to platform policy
save Latest Run receipt and terminal telemetry
```

The browser toolbar icon, whether pinned or under Extensions, opens the same in-page destination picker as the orb. It never chooses a default destination or starts a transfer before selection. Saved chats use the same early JSON capture, retry and delivery flow. Repeated toolbar messages keep the open picker and its capture; a click during a running transfer is ignored without a failure badge. The picker focuses on toolbar opening and uses the viewport's bottom-right corner if the composer orb is absent or has no size.

After empty-chat admission, destination preparation starts during the picker-to-handoff bridge, overlapping its 190 ms of motion rather than waiting for it. It opens beside the source tab in that tab's current window, with the source as its opener. The worker resolves the browser-supplied sender tab again before creation, including fresh recovery, so focusing another window or moving the source does not redirect the destination. A closed source fails preparation instead of opening in an unrelated window. Tab creation starts navigation; its response is not proof that the page or composer has loaded.

### Capture selection and failure handling

All five native chat downloads allow 32,000,000 bytes, including unused branches and site metadata. This shared allowance does not enlarge the selected transcript or supported text-file limits. ChatGPT retains its smaller 6 MB per-response bound for session and file-descriptor JSON. Existing capture deadlines still apply, so a larger allowed download is not a promise that every 32 MB response finishes in time.

Except after an exhausted temporary JSON retry, DOM capture of a saved chat starts immediately and launches one independent, fresh native JSON size check alongside source preparation/scrolling. It never reuses the picker/failed capture's history, retries the transfer, adds a visible step or waits for the count before continuing DOM work. The check counts selected chat text and supported text files it can actually read; a failed/incomplete file does not discard healthy files. This is a conservative observed count, not a claim that unknown files are empty or the full chat fits. Only an observed count above 4,000,000 stops the owning DOM attempt, at its next existing capture checkpoint, with the character-limit error before summary/paste. A failed, unavailable, pending or late count cannot delay/fail a completed DOM capture, replace DOM text, change another attempt or prove how long capture will take. DOM completion, cancellation and teardown abort the correlated count (including hook setup); the shared native-read queue waits for cleanup acknowledgement so an abandoned probe cannot hold up the next transfer. Cancellation IDs can never stop an ordinary capture. Bad file descriptors and unreadable attachment bodies are excluded from both measurement and normal JSON capture without discarding healthy text. Existing native identity/auth/transport/file-byte/deadline bounds and final capture limits still apply. Count data stays transient and is not another `diagnostics.json_attempts` entry; no database/telemetry schema change is required. Normal JSON capture still requires verified history and readable conversation/file text; attachment names alone cannot authorize capture. The same numeric-only measurement now returns the selected turn count. ChatGPT and the shared network readers also publish correlated numeric progress as soon as history is available, before supported-file downloads finish; that progress updates presentation only and never settles/releases the read queue. The final observed count still owns size enforcement and cleanup. If strict content/completeness validation fails after usable history arrives, measurement can salvage approximate turn/text counts for presentation only; those rough counts never authorize a size rejection or become a transferable transcript. Transport/auth/identity/download guards remain in force, so an unavailable native read can still leave no estimate.

JSON capture size rejections stop the transfer across all five platforms, including active replies, cached picker failures and size rejection on the one allowed temporary-error retry. Never retry a size rejection, scrape a smaller visible subset, summarize or paste it. A valid download can still exceed the transcript cap after its text attachments are included. Preserve the original capture detail/stage and measured JSON guard; report `conversation_too_large` without a DOM-fallback marker. The error says the chat/data is too large and displays only our applicable numeric limit, distinguishing transcript characters from attachment/response bytes. The user's measured size stays in diagnostics and is omitted from the message. Character-limit errors end with "Try a shorter chat." by owner request. Direct-text transfer above 4,000,000 characters also stops with the numeric character limit. Picker errors remain silent until destination selection; a destination already prepared concurrently may remain open unused.

- The picker always uses JSON-first capture and has no Speed toggle. Opening a saved chat's picker starts JSON capture; destination selection reuses the completed result or awaits that same read, including the immediate handoff with reduced motion enabled. Route/query changes, away-and-back navigation or changes to rendered turn identity/text invalidate the snapshot before and after awaiting it, triggering a fresh read. Closing the picker or teardown discards it. Native reads are serialized so a discarded in-flight read cannot cause a busy fallback. Already-issued native reads finish within existing bridge bounds; discarded results are never submitted or persisted. An unsaved chat uses DOM only after selection.
- Discarding a picker capture immediately releases its cached result, rendered-history copy and navigation guard. A native read already issued may finish within its bridge timeout, but its late result cannot restore the discarded snapshot. Terminal attempts also discard their unconsumed picker capture, including cancellation during handoff.
- An empty unsaved chat fails before handoff, capture or destination preparation. An unsaved chat with rendered turns can use DOM. Saved JSON chats may be captured before their native history mounts.
- Picker JSON errors stay silent until destination selection. A temporary failed prefetch or first fresh read gets one serialized fresh JSON retry before frontend failure or DOM recovery. ChatGPT retries immediately without an added timer; other source platforms retain their two-second cooldown. The retry stays inside the transfer deadline and rechecks cancellation and the original chat before issuing another request. Eligibility uses fixed diagnostics: network errors, timeouts, busy/unready hooks, missing auth/routing observation, or HTTP 408/429/500/502/503/504/529. Hard byte/transcript limits, invalid JSON/history/content, other HTTP rejection (including access denial), unknown failures and conversation/session changes are not retried. An attachment's explicit temporary HTTP status can qualify despite its broader incomplete category. The retry preserves the original attempt, source guard and deadline; it never creates another destination or summary. Successful recovery retains the safe capture cause and a local retry mark without a terminal error or DOM-fallback label. A rejected ChatGPT/Claude native response-body read is classified as `request_failed` / `network_error`, so it uses that same one fresh retry; discard every byte of the interrupted response and start the new read from the beginning. ChatGPT preserves this cause through session/history/paste-descriptor reads and their attachment wrapper. Decoder, JSON, structure and size rejection remain non-retryable; source/account cancellation and native deadlines keep their existing precedence. If the retry also fails with a temporary cause, all five platforms use normal DOM capture once, including ChatGPT. This exhaustion skips the independent native count/estimate probe rather than immediately making a third request to the same failing provider. DOM capture still enforces its normal final size and completeness checks. A hard/non-retryable second failure retains the existing platform policy. Unexpected ChatGPT plain-text entries retain readable JSON with a fixed `text_invalid` warning and a failed transfer outcome; they neither retry JSON nor scrape. Outside the active-reply snapshot below and the exhausted temporary-error retry above, other ChatGPT fast-capture failures show the capture error, release the attempt lock and never enter DOM preparation/sweeping or scroll the history sidebar. An already prepared destination may remain unused. Unsaved-chat DOM capture remains available. Other platforms retain their announced JSON-to-DOM recovery for non-size failures within the same attempt and prepared destination. Navigation, identity or session cancellation aborts instead of capturing a different chat. Only captured source text is submitted for summarization.
- A running or stopped reply is a snapshot of text already available, not a reason to wait for generation or reject otherwise valid JSON. Claude accepts current direct text/thinking blocks with null generation stop markers; DeepSeek accepts current fragments regardless of WIP/continuation markers; Grok uses returned own text despite assistant generation partial/inflight markers. Gemini retains the newest prompt if its reply is not yet present. Full history/branch, transport, attachment and size validation still apply. DOM capture detects visible native stop/streaming controls, with DeepSeek's outgoing native completion/continue XHR lifetime supplying its otherwise unlabelled control state. It freezes rendered verified text before preparation and never scrolls or waits for later text during an active reply. A failed ChatGPT JSON read can use this active-reply snapshot; other ChatGPT JSON failures remain terminal unless the temporary-error retry above is exhausted. Snapshot text is source-local, consumed once and released on reset/teardown.
- Destination selection pins the source route before its first await. A navigation latch follows preparation, DOM/attachment reads, JSON fallback and summary dispatch; away-and-back navigation cannot revive an attempt. Every capture result is checked before use, and terminal completion/teardown removes the guard's listeners and timer.
- Picker telemetry starts before empty-chat validation, so early exits are visible as safe metadata. A destination already prepared before a later failure may remain open unused.
- Source-local full-transcript recovery is available only after supported text was verified and captured. It handles summary-service failure, not missing/unverified capture.

### Paste and activation order

While the source handoff is at `paste_started`, its header offers **Copy instead** for the complete prepared carry, including short local transfers. Clipboard access starts in the click; automatic delivery is cancelled without closing the destination. Confirmation waits for the destination's cancellation acknowledgement (up to three seconds), and clipboard/worker waits are each bounded to four seconds. A missing worker inventory, unknown/lost acknowledgement or clipboard failure keeps the original copy dialog available; uncertain delivery uses its existing check-the-destination warning. A paste may already have landed before the click, so even confirmed copying asks the user to check the destination before pasting. The action releases its text/handler on completion or dismissal; late replies cannot restart delivery or replace a newer attempt. Manual takeover retains the existing `user_cancelled` outcome, not successful paste. No permission, schema, storage or normal-delivery round trip is added.

Pasting has its own maximum 60-second allowance, shortened by any earlier transfer deadline and sent as the destination's absolute write deadline. Expiry cancels automatic delivery while leaving its tab open and shows the existing unconfirmed-paste copy dialog with the ready carry. Every manual-takeover recovery dialog also uses that warning, including clipboard failure after a confirmed stop: stopping future writes cannot prove an earlier paste did not land. Capture/summary budgets, source/destination guards and the later normal backup/draft dialogs retain their existing behavior.

A prepared destination's first `editor_has_draft` rejection is returned immediately to the source copy dialog. It never opens a fresh destination or retries paste in another tab; other recoverable delivery failures retain their existing one-fresh-tab recovery.

On the first observed `editor_has_draft`, the destination immediately opens the compact “Your draft is safe” copy dialog before returning its failure acknowledgement. It says “We noticed your text box has text in it. Here’s your conversation, ready to be copied.” Its short preview omits only the exact local carry wrapper; Show more reveals the complete text, and Copy always uses the full prepared carry. If clipboard access fails, the complete text is selected for native or manual copy. The source also opens its original “Context is ready to copy” dialog with the same prepared carry. No second destination or paste attempt is created. A draft restored during delayed recovery uses the destination variant too. The draft guard still prevents insertion; copying confirms only after actual clipboard success. Expected draft recovery stays in metadata telemetry without a console error or `ERR` badge. Other failure and unconfirmed-paste messages retain their existing dialog variants.

Once the source copy dialog was actually displayed for `editor_has_draft`, Latest Run shows `copy_ready` (“Copy box shown”). The source records a bounded `local_fallback` event with code `editor_has_draft` after the UI acknowledgement. The existing relay/Edge wire format remains `failed`/`paste_failed` for compatibility; the SQL invariant trigger recognizes that exact marker at `paste_started`, stores `text_box` with no `failure_reason`, and retains the original cause in `diagnostics.error_code`. The database label describes the destination text box already containing text; previously acknowledged `copy_ready` rows use the same new label. This is a terminal handled outcome, distinct from successful paste or confirmed clipboard copy, and never increments failed-attempt counters. Verified remote summaries still count independently; local-direct counting retains its existing successful-delivery rule. Old draft errors without the acknowledgement stay unchanged, and a recovery UI failure stays failed. First terminal outcomes, signed receipts and identity protections remain immutable.

The insertion remains delivered; it cannot trigger a fresh-tab retry or a copy modal because the user subsequently changed it. Extension-owned insertion events and cursor-only movement do not cancel hydration recovery. Delayed recovery retries missing/disabled composer discovery every 180 ms within the normal paste retry window and remaining transfer time, including replacements caused by click/focus before writing. It allows one actual recovery insertion; an app that clears that retry receives manual copy rather than repeated writes. Restored/user drafts remain untouched. Recovery stops when conversation turns appear, at the transfer deadline, on replacement by another paste or on teardown; hidden tabs also release their recovery listeners/timers at expiry.

Every insertion guard checks absolute expiry after asynchronous source checks and around native click/focus and text-writing fallbacks. Elapsed time, not the expiry timer alone, forbids a late write. Disposed guards cannot resume insertion after replacement, cancellation or teardown. Click/focus that disconnects or disables a composer before writing returns to bounded discovery without consuming the one recovery insertion.

Textarea/input draft checks and paste verification use their live `value`, including an empty string. Static child text/defaultValue may retain a cleared draft and cannot prove composer content; contenteditable editors continue using rendered text.

Focused delivery (including all local carries) activates once before paste and does not activate again after verification; the user can switch away without being pulled back. Activation failure is reported, and a focus-required composer cannot receive an insertion after failed activation. A noninteractive, live-announced destination cue says `Pasting your context....`, then confirms verified insertion or directs the user back to source recovery. It never blocks composer controls or sends the message, and teardown removes it.

Remote summary completion fills its line immediately. Local carries use the short final sweep described below; neither path adds a completed-bar hold. The paste stage remains active before focused insertion and becomes complete only after verified inactive insertion. Remote source completion waits for two animation frames with a 120 ms fallback; local carries use bounded paint cues around their short sweeps. Hidden sources skip that wait; hiding during it releases it immediately and cleans up frames/timers/listeners. Suspended painting must not block activation or receipt saving. The timeline includes handoff finish, final activation and transfer completion.

### Near-end destination reveal

Remote summaries request one early reveal when the size-based display estimate reaches five seconds remaining, or sooner when the answer stream reaches its final `🔁 NEXT STEP` section after `📦 KEY CONTEXT`. The stream hint handles headings split across chunks, resets on provider retries and sends only an attempt ID to each live source sharing the request. A final result buffered with the hint skips optional messaging. This is evidence of the final section, not a guaranteed five-second provider deadline; the countdown remains an estimate for JSON-only backends and differently formatted answers.

Capture has already completed; only the attempt's prepared new-chat tab can be revealed. Before switching, the worker waits for native tab loading to complete with no pending navigation and a complete document. It deliberately does not wait for a usable composer: some hidden chats finish composer hydration only after focus. Actual paste still waits for a usable composer and preserves restored/user drafts. Readiness checks mount no UI and never focus or reload the page. After switching, it shows one `Polishing your summary…` cue with `It will be pasted here when it’s ready.` while the real summary remains pending, then `Pasting your context....` when the existing paste message arrives, and the verified ready cue afterward. The cue mounts outside the page body so body replacement cannot erase it; duplicate status messages reuse the same node and expiry instead of redrawing it. All optional readiness work shares the six-second budget. If generation overruns, the polishing cue stays until delivery, failure, cancellation, teardown or the attempt deadline.

Short/direct carries and remote results that arrive before the threshold follow the normal reveal sequence without an added wait. Early status readiness is bounded to six seconds and failure falls through to normal delivery. Summary completion or failure stops pending optional readiness immediately without cancelling actual delivery; source navigation and teardown also stop that presentation work. An already-submitted native activation finishes its window focus under the real transfer token. An in-flight reveal settles before paste to prevent a late cue/focus from replacing delivery. Destination completion/cancellation latches the attempt so a queued status message cannot recreate polishing after real paste or failure. The worker records the earlier focus so later paste/final activation does not pull the user back again; the existing native activation-settle minimum, source/destination checks, draft protection, cancellation and fresh-tab recovery remain. A recovery tab has its own normal activation.

### Deadlines and locks

The page-local `isRunning` lock starts with a six-minute absolute `deadlineAt`. DOM preparation immediately grants at least 20 minutes of scrolling plus six minutes for summary/delivery. A usable estimate can grow scrolling to twice its estimated duration plus two minutes, capped at two hours; it never shortens the allowance. Capture completion restores at least six minutes of delivery headroom. The deadline follows continuation, summary, preparation/activation, paste retries and delayed recovery.

The source resets its watchdog and sends top-frame, source-owned `EXTEND_DOM_CAPTURE_DEADLINE`. The worker updates only the existing live operation/expiry, preserving destinations and cancellation; it cannot revive expired/cancelled work or change another source's attempt. Its storage queue also refreshes the saved active report for interruption reporting across sleep/restart, without a new event or delayed acknowledgement. Expiry records `client_interrupted`, shows a timeout and releases the owning lock; late work cannot resume it or unlock a newer attempt.

Cancellation and ownership:

- Closing the source immediately revokes work before telemetry I/O. Preparation, summary waits, retry, delivery and activation check ownership. `CANCEL_TRANSFER` stops source continuation and destination insertion/recovery; destination checkpoints also use `CHECK_TRANSFER_ACTIVE` to verify source existence after lost notifications/restart.
- Closing a destination leaves capture, summary and telemetry active. A missing prepared tab can use the existing one-fresh-tab recovery. A paste transport error permits this only when the tab is confirmed missing; a lost live-tab acknowledgement remains unconfirmed. If source closure overtakes an in-flight tab creation, remove that newly created tab when its response arrives; preserve pre-existing tabs/drafts.
- Trusted Escape in the source handoff or revealed destination cancels locally, hides cues, stops countdown/recovery and releases the source lock before worker/network acknowledgement. Send `CANCEL_TRANSFER` before receipt serialization/terminal telemetry. The worker accepts only the owning source or associated destination's top frame, revokes first, submits native removal of attempt-created tabs, then broadcasts/cleans up. Pending creations are removed on completion; cancellation never starts recovery or closes source/pre-existing tabs merely because they were associated.
- The last cancelled summary waiter aborts backend fetch/body; response disconnect aborts provider work, reservations and retry waits. Other live attempts sharing the summary can finish. Cancelled tokens reject queued preparation/summary/reveal/paste; late replies cannot show errors or reset newer attempts. Synthetic attachment Escape does not cancel; Escape in the picker only dismisses it. Already inserted text, receipts and accepted upstream work are not undone.
- Native source-tab `status: "loading"` destroys the old document: cancel owned work and queue `client_interrupted` / `conversation_changed` at the last stage, without guessing whether an unacknowledged paste happened. Ignore destination/non-loading updates and completed/expired/newer attempts. Events retain no URL. Source close remains `user_cancelled` / `source_tab_closed`.

Paste needs an explicit boolean `ok` acknowledgement. A live destination's timeout, invalid/missing reply or transport rejection (except known missing receiver) becomes `paste_unconfirmed`: no re-send or new fallback tab when context may already be there. Missing-receiver/connection-establishment failures retain injection retries; explicit `{ ok: false }` retains fresh-tab recovery. Preserve the full carry for manual copy, tell the user to check the existing destination, and retain `paste_failed` telemetry.

After extension reload, old isolated worlds may survive reinjection. Owned events, observers and timer/frame callbacks check runtime liveness. An invalidated world releases listeners/observers/recovery/timers without removing replacement-owned UI. A dead summary-message connection asks for a tab refresh; it cannot enter local recovery against a dead worker. Ordinary backend/network failures still allow exact local recovery. Old page code may need one refresh after updating.

Operation tokens/destination associations are memory-only. Restart cannot restore complete delivery ownership: lost preparation can orphan a tab, lost delivery can require manual recovery, and shutdown may lose an unpersisted final result. Source-existence/loading checks are not a persisted delivery protocol; restart reconciliation/resumption remains deferred.

Both picker entry points call `beginTransferAttempt` only after selection. Clicking during a run creates no second attempt, failure or Latest Run receipt. An admitted empty chat records `no_conversation` and immediately unlocks.

### DOM preparation and sweep

The supported DOM path runs on all five platforms for unsaved chats and the supported announced JSON fallback:

1. Reset per-transfer pasted-card state and cached scroll roots.
2. Scroll the actual conversation root to the top instantly; wait for stable turn count, characters, height and scroll position.
3. Expand verified collapsed content and supported pasted cards. Never click popup/menu triggers, response actions or controls inside menus/dialogs. Gemini text expanders must belong to user-query or response-text content, rather than the whole response action area.
4. Capture a rendered window and advance through the conversation with ordered overlap.
5. Active transfers stop at bounded quiet/no-movement/stale conditions or their cancellable deadline. They no longer return a prefix merely after 480 advances; the 480-advance guard remains only for standalone capture calls without an owning transfer. `scrollIntoView` is only a boundary fallback.
6. Sequence-align windows with the initial baseline. Fuller matching text may replace shorter text; partial text must not downgrade a turn.
7. Serialize `<Platform> conversation:` with `User:` / platform-role turns separated by blank lines.

Claude/ChatGPT preparation allows 4.5 seconds, other sites 1.8 seconds, normally requiring three stable samples. Standard sweep advances 60% of a viewport; proven ordered overlap can permit 90% steps.

Grok's adaptive profile uses two 40 ms preparation samples, two samples within a 100 ms fast settle, 70% steps until overlap is established then 90%, 10 ms change polling and a 160 ms terminal quiet check. A physical scroll with no immediate window change gets up to 220 ms for delayed virtualization. Preserve role validation, sequence alignment, deduplication and bounds when adjusting speed.

Turn selection and deduplication:

- Exclude nav/header/footer/aside/menu, active composer descendants/ancestors, prompt suggestions and Cap Context UI. Require role evidence from platform selectors, role attributes or semantic ancestors within eight levels; loose `you` / `me` labels do not qualify.
- Containment scoring keeps true message boundaries and rejects page/conversation wrappers. Claude message wrappers own their paragraph/code descendants as one turn.
- ChatGPT's scroll root is the nearest structural-turn ancestor with computed `overflow-y: auto|scroll`, not a generic large/scrollable element. Structural `conversation-turn-*` / `data-message-id` identities collapse duplicate copies while preserving repeated text in separate turns.
- Other DOM adapters deduplicate exact role+text. This avoids virtual-window inflation but can remove genuine repeated turns; a change needs paired repetition and overlap regressions.
- DOM capture retains verified one- and two-character turns in both the initial snapshot and later scrolling windows, regardless of conversation length. Sweep settling uses that same turn set for its signatures, so a final window containing a short reply can reach the normal quiet stop. Short control labels are excluded. Empty-state copy and unverified page text fail closed; the separate empty-chat and destination guards retain their existing detection threshold.
- Claude/ChatGPT pasted-card readers open recognized cards, collect normal or virtualized `[data-index]` rows in order, close the panel and reattach full payload to its owning user turn after remounts. State resets each transfer.

Long native ChatGPT DOM chats have historically under-captured. Simulated virtual windows verify the merge algorithm, not completeness of a currently rendered live chat.

### 4M large-chat transfers

### Configured provider order

Provider HTTP failures inspect at most 8 KiB of error JSON for at most 150 ms within the existing attempt deadline. Only allowlisted upstream code/type, a fixed canonical message (capped at 120 characters) and bounded retry-after milliseconds enter server diagnostics; raw/unknown message text is never saved. Error-body cleanup is not awaited. These additive fields need compatible database/Edge validators before backend rollout; local migrations alone do not deploy them.

Named provider request-ID headers may supply one ASCII correlation token of 8–128 characters; controls, URLs and arbitrary body fields are rejected. HTTP-200 JSON/SSE errors, choice-level errors and Google safety feedback are identified before success validation and retain the same safe code/type/message metadata. ### Prompt and output policy

`api/summary-prompt.js` owns `getSummarySystemPrompt()`, `getContextCarryTemplate()`, title and trusted destination instruction; `api/summarize.js` imports them for requests, normalization and local recovery. `legacy/SKILL.md` is not runtime input.

JSON capture submits `{ platform, messages, telemetry? }` without a duplicate transcript. Accept only the five platforms and nonempty ordered entries containing exactly user/assistant `role` and `text`, plus validated telemetry. Reconstruct speaker-labelled text only for character/byte limits, profile/timing and exact backend recovery. The **4,400,000-byte request limit** includes escaping/array overhead. Deploy structured-input support before the client; older backends reject it and clients use local recovery.

Providers receive one system prompt plus a user JSON envelope: `schema: cap-context-conversation-v2`, `dataType: untrusted-conversation-transcript`, platform and original messages. Roles remain untrusted data, never API/system/tool authority; preserve text including outer whitespace and do not split quoted role labels. DOM/older clients retain `{ conversation, telemetry? }` and the v1 string envelope without guessed boundaries. Both are untrusted history.

Output title: `CONTEXT CARRY — READY TO PASTE`; sections once, in order: WHO I AM, WHAT WE WERE DOING, WHERE WE LEFT OFF, DECISIONS MADE, OPEN QUESTIONS, KEY CONTEXT, NEXT STEP. The v21 prompt stages are read safely, collect across the entire chat, fill sections, check. Keep each section's guidance together; standalone headings belong only to the final template. One generation per attempt; prompt instructions do not prove grounding.

Preservation rules:

- Distinguish reported facts, user identity/named owners, accepted choices, proposals/rejections/deferred options and prohibitions. An unlinked owner is neither confirmed nor excluded as the user. Observed integrity is a fact, not an invented requirement; not-started/undecided states create no action gates.
- Preserve latest request/stopping point in WHERE WE LEFT OFF and essential current draft/code/formula/reproduction in KEY CONTEXT, verbatim where wording matters. Artifact pointers include purpose and supplement essential content the destination may not access. Fixed NEXT STEP confirmation is separate from the still-pending task; do not answer it or convert it to a missing-evidence checklist.
- Distinguish inspection/review/proposal permission from implementation. Exclude newly computed arithmetic, diagnoses, recommendations, drafts/plans; request important prohibitions verbatim and check source/coverage. No fictional worked examples: their facts leaked into unrelated outputs.
- From `HANDOFF_SKILL.md`: keep explicitly stated reasons for accepted decisions; observed failed results/abandonment reasons; separate implementation/test/deployment status; artifact purpose. Unsupported reasons/status stay omitted/unknown, never invented NOT STARTED. Keep local versus external verification scope. The imported reference remains separate from the backend prompt.

Shorter v15–v17 prompts failed repeated grounding checks; v21 retains full fact/source/status collection. Historical evidence and limits: [v15 comparison](https://github.com/spidey889/context-generator/blob/25e856e/docs/handoff-quality-v15-comparison.md), [clarity comparison](https://github.com/spidey889/context-generator/blob/25e856e/docs/prompt-clarity-v20.md), [adaptations](docs/handoff-quality-adaptations.md). Judge live improvement against a baseline; structure or structured input cannot establish factual accuracy/faster inference.

Keep two independent decisions:

1. **Deliverability:** reject refusal-only/substantively empty output after removing recognized scaffolding/placeholders/trusted instructions, and recognizable opening replies that refuse reasoning reproduction then offer their own thought-process summary. Advance existing routes with the full input and record metadata-only `provider_output_rejected`. This conservative English check does not prove semantic coverage. Quoted refusal, contextual inability to connect/build, refusal alongside useful context, short useful text and useful token-limited text remain deliverable.
2. **Advisory diagnostics:** malformed/missing/duplicate headings, shortness and finish reason flag useful output without rejecting it. `validateContextCarrySummary()` has no source transcript; it cannot detect fluent hallucinations or prove grounding.

Strictly structured output gets fence/legacy-footer removal, canonical headings, Unicode box and replaced NEXT STEP. Other deliverable text gets trusted NEXT STEP, then retains the first of identical NEXT STEP bodies (ignore outer whitespace/line endings); exclude headings in quotes, indented examples and code fences. Preserve different bodies/all other text; invent no sections. Diagnostics describe original provider output.

Bounded `validationReason` / `qualityFlags`: `bad_structure`, `missing_section`, `duplicate_section`, `token_limit`, `too_short`, `refusal_like`. Log only flags/reason and word count; they are not Supabase telemetry. Tiny/emergency local-direct uses empty flags/null reason. Advisory floor: 20% of target, clamped to 80–200 substantive words. Large-profile `minWords` / `qualityFloorMet` is diagnostic, never a prompt minimum/rejection threshold. Exact heuristics/limits: [summary validation](docs/summary-validation.md); historical evidence: [accuracy pass](https://github.com/spidey889/context-generator/blob/25e856e/docs/summary-accuracy-pass.md).

### Outbox and ingress availability

- Queue writes are independent of network delivery. Capture prepares a bounded memory snapshot, retained for six minutes or the longer owning DOM operation deadline after resolving the install UUID and original attempt/version identity. Elapsed transfer/transport time and abort state are checked before a backend request and before accepting its result, so storage cannot extend either deadline or cache late success. If storage stays unavailable or the worker stops before persistence, telemetry may be lost while the summary remains usable.
- Per-attempt compaction keeps monotonic progress, first terminal outcome and the first signed receipt paired with its authenticated version. An in-flight acknowledgement removes only the revision actually sent.
- A rejected local outbox append retains the current event/receipt in the existing active store with `outboxPending`; startup and retry recover it without another source message. Clear that marker only after an outbox commit, and retain pending terminal/proof copies ahead of ordinary active snapshots within the existing 500-entry bound. Optional active-store failures cannot prevent a healthy local queue from draining. Acknowledgements reject invalid events and failures of both stores rather than claiming durable acceptance.

Worker/relay requests refuse redirects; the worker omits cookies. Unexpected responses retain the client report for retry, or produce the existing fixed server logging warning after its bounded retry window.

### Diagnosis starting points

| Symptom | First place to inspect | Do not infer |
| --- | --- | --- |
| Orb missing/misplaced after sending, account/layout change or resize | Current visible composer DOM; platform `find*InlineToolbar`, ownership/markers, observer scope and picker invalidation | A free plan necessarily lacks controls, or a generic/fixed anchor is safe for Claude |
| JSON capture falls back or captures the wrong branch | Hook readiness/ownership, pinned chat/account, route/auth observation, serializer completeness and cancellation | A worker installation acknowledgement proves MAIN readiness |
| DOM capture loses/duplicates turns | Actual scroll root, virtual overlap, role boundaries and stable IDs | Simulated window tests prove full live-chat history |
| Pasted carry disappears or user draft changes | Ready editor identity, pre-focus draft, verification and post-activation recovery | A successful insert event proves stable delivery |
| Useful summary has quality flags | Content gate versus advisory validator, finish reason and actual deployed model | Bad structure should discard useful context, or good structure proves grounded facts |
| Latest Run model differs from telemetry model/NULL | Display alias, actual response model, v3 receipt, source-local/cache/legacy path | The requested primary model served, or NULL is always an ingestion defect |
| `transfers` stays started or counts look low | Outbox/revision delivery, terminal report and signed receipt/counter eligibility | Started means failed, or successful paste necessarily proves summary work |
| Local checks pass, live evaluation fails | Exact subcommand, deployment commit/alias/environment and provider output | All validation modes check the same artifact or failure category |

Current limits worth preserving in assessments: JSON checks cannot prove absence of unmarked server omissions; DOM role+text can lose real repetitions; summary validation cannot establish semantic grounding; paste verification allows 5% missing normalized words; telemetry can drop bounded old/capacity reports; automated browser evidence is Brave/fixture based. Report those practical boundaries when they affect a conclusion, rather than promoting a test pass into a broader product guarantee.

### Local protected preview testing

For a temporary unpacked-extension test, set a short-lived VERCEL_OIDC_TOKEN in the current process environment, then run `node scripts/set-local-preview-backend.js https://<exact-preview-host>.vercel.app` and reload the canonical extension. The helper grants only that host, routes summary and telemetry together, and stores the origin-bound token in ignored `extension/local-preview-auth.js`. It adds the worker import only while that file exists, and production restoration removes the import before deleting the file. Never leave a missing optional script referenced by the shipped worker: Chromium can reject its installation even when the import is caught. Run `node scripts/set-local-preview-backend.js production` and reload afterward; this removes the local token and restores production. Firefox packaging refuses a preview configuration.
